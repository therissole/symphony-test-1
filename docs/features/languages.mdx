# Languages Capability

`Languages` is a capability containing five independent request slices. It is not one CRUD slice.

| Slice | Route | Purpose |
| --- | --- | --- |
| `ListLanguages` | `GET /api/languages` | Return the catalog ordered by name |
| `GetLanguage` | `GET /api/languages/{id}` | Return one language |
| `CreateLanguage` | `POST /api/languages` | Validate and create a language |
| `UpdateLanguage` | `PUT /api/languages/{id}` | Validate and replace language fields |
| `DeleteLanguage` | `DELETE /api/languages/{id}` | Delete a language and cascade greetings |

Each slice owns its response projection and SQL. There is no `LanguageRepository` or shared
`Language` persistence model.

## Contracts

Create and update accept:

```json
{
  "name": "French",
  "code": "fr"
}
```

Name is required and limited to 100 characters. Code is required and limited to 10 characters.
The database also enforces unique names and codes.

Successful reads and writes return:

```json
{
  "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "name": "French",
  "code": "fr",
  "createdAt": "2026-07-23T10:30:00Z",
  "updatedAt": "2026-07-23T10:30:00Z"
}
```

## Slice-specific implementation

- Queries project directly into their own response records.
- Create and update keep their FluentValidation `RequestValidator` nested in the slice and invoke
  it asynchronously before opening a database connection.
- Create and update use `RETURNING` to avoid a second connection and race window.
- Unique name or code violations are translated to `409 Conflict`.
- Delete relies on the database foreign key's `ON DELETE CASCADE` behavior.
- All database work receives the HTTP request cancellation token.

## Authorization

OpenFGA grants the bootstrap superuser full control. Standard users may list and view every
related language but receive `403 Forbidden` for create, update, and delete. Every language is
linked to `system:global` when it is created; provisioning also reconciles existing language and
greeting records. Deleting a language removes its own tuple and the tuples for greetings removed
by the database cascade.

## Tests

The language integration suite covers listing, get/not-found, valid and invalid creation,
uniqueness conflict, get/update, update/not-found, and delete/not-found. Unit tests cover
deterministic validation rules, while the cross-capability cascade is verified end-to-end.
Request-level LightBDD acceptance fixtures cover every language slice through API and browser
drivers: superusers can read and write, standard users can read, and rejected standard-user writes
show the public denial message without changing state. API-only scenarios prove authorization runs
before create and update validation.
