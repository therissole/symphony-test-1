# Greetings Capability

`Greetings` contains six request slices:

| Slice | Route | Purpose |
| --- | --- | --- |
| `ListGreetings` | `GET /api/greetings` | Return greetings ordered by text, optionally filtered by language, formality, or creation range |
| `GetGreeting` | `GET /api/greetings/{id}` | Return one greeting |
| `GetGreetingByLanguage` | `GET /api/greetings/by-language/{code}` | Return a purpose-built language view |
| `CreateGreeting` | `POST /api/greetings` | Validate and create a greeting |
| `UpdateGreeting` | `PUT /api/greetings/{id}` | Validate and replace greeting fields |
| `DeleteGreeting` | `DELETE /api/greetings/{id}` | Delete a greeting |

## Purpose-built query

`ListGreetings` accepts optional `languageId`, `formal`, `createdFrom`, and `createdTo` query
parameters. The creation range uses RFC 3339 UTC instants, an inclusive lower bound, and an
exclusive upper bound. The slice validates that `createdTo` is later than `createdFrom` before it
opens a database connection.

`GetGreetingByLanguage` executes one tailored join and projects directly into:

```json
{
  "language": "English",
  "languageCode": "en",
  "greetingText": "Hello",
  "formal": false
}
```

An optional `formal=true|false` query parameter filters the result. Without the parameter, informal
greetings sort first. This query does not load a generic greeting and then perform a second
language lookup.

## Command contract

Create and update accept:

```json
{
  "languageId": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "greetingText": "Bonjour",
  "formal": true
}
```

`languageId` must be non-empty and reference an existing language. `greetingText` is required and
limited to 255 characters. A missing language returns a validation problem keyed by `languageId`.
Create and update define a nested FluentValidation `RequestValidator` and invoke it asynchronously
before database I/O.

Commands use PostgreSQL `RETURNING` for atomic responses. Every database call carries the HTTP
request cancellation token.

## Referential integrity

The database owns the relationship:

```sql
FOREIGN KEY (language_id)
REFERENCES languages(id)
ON DELETE CASCADE
```

Deleting a language therefore deletes its greetings without cross-slice orchestration code.

## Tests

Integration tests cover list filters, get/not-found, formality filtering, create/update,
missing-language validation, and delete/not-found. LightBDD acceptance tests sit in request-level
acceptance slices, defaulting to both API and browser protocol drivers without sharing application
types. The date-range scenario is deliberately API-only because it exercises the public,
test-environment clock contract.

See the [Greetings API reference](/api-reference/endpoints/greetings/list-greetings) for exact
contracts, status codes, and an interactive request playground.
