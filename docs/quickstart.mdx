# Quick Start

## Prerequisites

- [Docker](https://www.docker.com/get-started) with Docker Compose
- [.NET 10 SDK](https://dotnet.microsoft.com/download) for local development
- [Aspire CLI](https://aspire.dev/get-started/install-cli/)
- [Node.js](https://nodejs.org/) 20.17 or later for the Mintlify preview
- Git

## Run with Aspire

```bash
git clone https://github.com/therissole/symphony-test-1.git
cd symphony-test-1
aspire run
```

The Aspire AppHost starts:

- PostgreSQL 18 with environment-local ephemeral data
- Keycloak with the committed local `symphony` realm
- A one-shot .NET migration resource
- The API and hosted Blazor WebAssembly administration UI after all migrations complete
  successfully
- The local Mintlify documentation preview

Open the **Symphony administration** endpoint shown in the Aspire dashboard to use the dashboard,
languages, and greetings UI. Sign in as `symphony-admin` with the temporary password
`ChangeMe!12345`; Keycloak requires a new password on first sign-in. The documentation resource
reloads as files under `docs/` change. In
the documentation, open **API Reference**, select an endpoint, and choose **Try it** to send a
request to the running API.
The endpoint pages are generated from the API's live Development OpenAPI document each time the
documentation resource starts.

Use the API endpoint to exercise the slices:

```bash
curl <api-endpoint>/api/health
```

Health is public. Language and greeting calls require a bearer token obtained through the
interactive OIDC sign-in flow.

To run another instance with randomized ports and isolated user secrets:

```bash
aspire run --isolated
```

Aspire allocates independent endpoints for the application, Keycloak, PostgreSQL, and the other
resources in that run. The AppHost injects the resolved Keycloak realm authority into the API; the
browser then obtains that authority and the public client ID from
`/api/authentication/configuration`. There is no fixed Keycloak port in the Aspire application
model. PostgreSQL intentionally uses container-local storage so randomized isolated credentials
cannot be paired with data initialized by a previous run. Use Docker Compose when local database
persistence across environment restarts is required.

Use a separate browser profile for each environment when signing into both at once. Keycloak
cookies are scoped by host and path rather than port, so two `localhost` instances using the same
realm name otherwise share browser cookie scope even though their service ports are different.

The Development OpenAPI document is at `<api-endpoint>/openapi/v1.json`. Aspire also exposes
platform readiness and liveness endpoints at `/health` and `/alive`; the existing `/api/health`
slice remains the database-aware public API contract.

## Fast edit/verify loop

Use this workflow when iterating on a slice. The AppHost preserves the isolated environment and
its dynamically allocated endpoints while watching its C# project resources:

```powershell
aspire config set features.defaultWatchEnabled true
aspire run
```

Keep the watcher open. The dashboard and startup output identify the isolated **Symphony
administration** endpoint for that run. Do not manually tear down and recreate PostgreSQL,
Keycloak, or migrations after an application or UI edit, so an agent can verify a change directly
instead of rebuilding the stack. If a change is not visible, rebuild only the API resource from the
dashboard or with `aspire resource api rebuild`:

```powershell
Invoke-RestMethod <Symphony-administration-endpoint>/api/health
```

Open or reload the same administration endpoint to test the hosted browser client against that
same API. After Aspire restarts or rebuilds a resource, wait for the health request to succeed
before navigating or reloading. Stop the watcher with Ctrl+C when done. This workflow does not
hard-code ports, so it can run alongside other isolated development or test environments.

The Compose command below is a headless image build for reproducible checks. It is not the
hot-reload loop: `docker compose up --build` bakes the current source into the API image, so it
needs a rebuild to observe a source edit.

## Run with Docker Compose

Docker Compose remains available for a fixed-port, headless environment and uses the same
migration executable:

```bash
docker compose up --build --wait
curl http://localhost:8081/api/health
docker compose down -v
```

Docker Compose exposes Keycloak at `http://localhost:8180` and the application at
`http://localhost:8081`. Set `SYMPHONY_API_PORT`, `SYMPHONY_KEYCLOAK_PORT`, or
`SYMPHONY_POSTGRES_PORT` before starting Compose to override the defaults. Compose derives the
browser-visible Keycloak authority from `SYMPHONY_KEYCLOAK_PORT`. Its committed realm allows
all redirect URIs and web origins for local development only because Keycloak does not support a
wildcard in the URI port. Replace those wildcards with exact deployed URLs outside local
development.

## Run tests

Docker must be running because integration and end-to-end tests create isolated PostgreSQL
containers. Build once, then install the Playwright browser runtime before the first browser-test
run:

```bash
dotnet build symphony-test-1.slnx --configuration Release
pwsh tests/e2e/symphony-test-1.E2ETests/bin/Release/net10.0/playwright.ps1 install chromium
dotnet test symphony-test-1.slnx --configuration Release --no-build
```

Run suites individually:

```bash
dotnet test tests/unit/symphony-test-1.UnitTests/symphony-test-1.UnitTests.csproj
dotnet test tests/ui/symphony-test-1.WebTests/symphony-test-1.WebTests.csproj
dotnet test tests/integration/symphony-test-1.IntegrationTests/symphony-test-1.IntegrationTests.csproj
dotnet test tests/e2e/symphony-test-1.E2ETests/symphony-test-1.E2ETests.csproj
```
