# Architecture

This reference follows Jimmy Bogard's definition of Vertical Slice Architecture: treat each
request as a distinct use case, group its concerns front-to-back, minimize coupling between slices,
and maximize cohesion inside a slice.

## The unit of architecture

A capability is not automatically a slice:

```text
Languages                         capability
├── ListLanguages.cs              query slice
├── GetLanguage.cs                query slice
├── CreateLanguage.cs             command slice
├── UpdateLanguage.cs             command slice
└── DeleteLanguage.cs             command slice
```

Every request file owns:

1. Route and OpenAPI metadata
2. Request-specific input and output records
3. A slice-local FluentValidation validator when the request has rules
4. Handler flow
5. Tailored parameterized SQL
6. Projection into the response
7. Expected failure translation

The feature registration file only composes the capability's routes.

## Request flow

```mermaid
flowchart LR
    Client["HTTP client"] --> Pipeline["ASP.NET Core pipeline"]
    Pipeline --> Authentication{"Authenticated?"}
    Authentication -->|No| Unauthorized["401 Unauthorized"]
    Authentication -->|Yes| Slice["One administration request slice"]
    Slice --> Validation{"Input valid?"}
    Validation -->|No| ValidationProblem["400 Validation Problem"]
    Validation -->|Yes| Database["Npgsql + request-specific Dapper SQL"]
    Database --> Result["Typed HTTP result"]
    Slice -. unexpected failure .-> ProblemDetails["Global Problem Details"]
```

There is no application-wide service or repository gate. A query can use a purpose-built join while
a command can use `INSERT ... RETURNING`. Each slice chooses the simplest pattern that fulfills its
request.

## Anatomy of a slice

`CreateLanguage.cs` contains nested `Request` and `Response` records, an internal
`RequestValidator : AbstractValidator<Request>`, a `Map` method, and the handler. The handler:

1. Receives `IValidator<Request>` from dependency injection and calls `ValidateAsync` before
   opening a connection.
2. Opens a connection from the shared `NpgsqlDataSource`.
3. Executes parameterized SQL with a cancellation-aware `CommandDefinition`.
4. Uses PostgreSQL `RETURNING` to produce the response atomically.
5. Maps only the expected unique constraint violation to `409 Conflict`.
6. Lets unexpected exceptions reach centralized exception handling.

Keeping these decisions together makes the use case understandable and changeable in one place.

## WebAssembly UI slices

The MudBlazor client is a standalone Blazor WebAssembly project and an independent Aspire resource.
The API does not reference or host it. A small YARP gateway preserves the browser's single public
origin: during development it proxies UI requests to the Web development server and `/api`
requests to the API; in published deployments it serves the compiled WebAssembly assets and still
proxies `/api`. The client does not reference the API assembly, persistence packages, or server
DTOs. It calls relative `/api` routes over `HttpClient`, so development and deployment remain
same-origin without CORS or browser-side endpoint configuration.

This resource boundary is also the hot-reload boundary. Aspire can watch and rebuild `web`
independently from `api`, so a UI edit no longer requires rebuilding the API's static-web-assets
manifest. The AppHost runs both with their native `dotnet watch` development commands; its own
restart-based watch is disabled for the normal inner loop. The gateway itself changes only when
routing or hosting policy changes.

UI use cases follow the same cohesion rule as API requests:

```text
Features/Languages/
├── ListLanguages.razor
├── CreateLanguage.razor
├── ViewLanguage.razor
├── UpdateLanguage.razor
└── DeleteLanguage.razor
```

Each component owns the HTTP operation, the smallest request and response records it consumes,
loading and failure states, and interaction flow. Similar records are intentionally repeated
between operations because they may evolve independently. The client has no resource-wide API
clients, services, repositories, or shared server contracts.

Only stable presentation mechanics are shared: the application shell, page header, loading/error
states, and RFC 7807 parsing. `MudDataGrid` performs client-side sort, quick search, column filters,
and paging because the reference endpoints return the complete small catalogs. A larger dataset
should introduce a dedicated server-side search/list slice rather than hiding paging policy in a
generic client.

Health is deliberately absent from the administration navigation. It remains an operational
contract for orchestrators and diagnostics, not a user-managed catalog capability.

## Authentication boundary

Authentication is shared platform infrastructure, not a business slice. Aspire starts Keycloak
and imports a local realm. The WebAssembly client uses a public OIDC client with authorization code
and PKCE, then attaches access tokens only to same-origin API calls.

The `/api` route group requires authorization by default. `/api/health` explicitly opts out with
`AllowAnonymous`; `/api/authentication/configuration` also opts out because it exposes only the
current public authority and client ID required to initiate OIDC. Language and greeting groups
inherit the protected default. The API validates issuer, audience, signature, signing key, and
lifetime. Protecting Razor routes provides the user experience, while API authorization remains
the actual data boundary because browser-delivered code is always inspectable.

Aspire does not pin Keycloak to a host port. It resolves an available endpoint for each run and
injects that realm authority into the API. The browser loads the corresponding public
configuration from the same-origin API before registering OIDC, which keeps multiple isolated
Aspire environments independent.

## What is shared

Shared code is intentionally small:

| Shared concern | Why it is shared |
| --- | --- |
| Aspire Npgsql client integration | Connection pooling, health checks, and telemetry are platform mechanics |
| Global Problem Details | Unexpected failures need one safe response policy |
| OpenTelemetry logging | Exports structured `ILogger` events with active trace and span context |
| Aspire service defaults | Captures telemetry and supplies platform health and resilience |
| Same-origin gateway | Preserves browser routing while allowing independent API and Web resources |
| Keycloak/JWT authentication | Identity validation and request authorization are platform boundaries |
| FluentValidation registration | Discovers internal validators while rules remain inside slices |
| Typed entity IDs | Prevents cross-entity UUID mistakes while preserving UUID wire contracts |
| Capability route registration | Composes slices without owning their behavior |
| UI shell and state components | Stable visual behavior shared by unrelated pages |
| RFC 7807 client parsing | HTTP error mechanics without resource-specific behavior |

Database migrations remain centralized because the sample uses one relational schema. The AppHost
runs the migration project to completion before it starts the API. The runner serializes concurrent
attempts with a PostgreSQL advisory lock and rejects changes to an already-applied migration by
comparing its checksum. A larger modular system could own migrations per module without changing
the slice design.

## What is not shared

The project deliberately avoids:

- Resource-wide repositories
- Generic repositories
- Application-wide CRUD services
- Shared persistence entities used as API contracts
- One request/response model reused across unrelated operations
- Broad exception catching inside slices
- A mandatory handler dispatch library

Small mapping or validation duplication is acceptable when it prevents two requests from becoming
coupled. Extract a shared concept only when it has stable meaning beyond coincidentally similar
code.

## MediatR and CQRS

The read and write use cases naturally have different models and SQL, which provides practical
command/query separation. MediatR is not required to achieve this. This reference uses direct
Minimal API delegates so the request flow remains visible.

MediatR can be introduced when its dispatch or pipeline behavior solves a demonstrated problem. It
should not be added merely as an architectural badge.

## Validation and errors

- Command request rules use FluentValidation's strongly typed fluent API.
- Each validator is nested in its owning slice rather than placed in a parallel validation layer
  or a separate file.
- Validators are registered by assembly scanning, injected as `IValidator<Request>`, and invoked
  explicitly with the request cancellation token.
- Error property names are overridden where necessary to preserve lower-camel-case JSON contract
  keys such as `languageId` and `greetingText`.
- Invalid input returns `application/problem+json` validation details.
- Missing resources return `404 Not Found`.
- Anonymous administration requests return `401 Unauthorized`.
- Language uniqueness violations return `409 Conflict`.
- Greeting foreign-key violations return a `400` validation problem on `languageId`.
- Unexpected exceptions are logged and rendered safely by global Problem Details.
- Health failures return `503` without exposing connection or exception details.

OpenAPI metadata on each slice declares the same result set implemented by the handler.
Each route also supplies a concise summary and a behavioral description. XML documentation on
slice-local request and response records describes their JSON fields in the generated schema.
Because those contracts intentionally share the nested names `Request` and `Response`, the
composition root prefixes OpenAPI schema reference IDs with the declaring slice name so every
contract remains distinct.

`LanguageId` and `GreetingId` are stable cross-cutting identifier primitives, not shared endpoint
DTOs. Minimal API parsing, JSON converters, Dapper type handlers, and OpenAPI transformations keep
them as UUID strings at every external boundary while preventing accidental assignment between
entity types inside the API.

## Transactions and domain logic

The sample's commands each require one SQL statement, so they do not need explicit transactions.
When a use case requires multiple atomic writes, its slice should own the transaction boundary.

Start with a transaction script. If business rules become complex, refactor that slice toward the
appropriate domain model or service. Do not impose one domain pattern on every request.

## Testing aligned to architecture

```text
tests/unit/Features/             deterministic slice rules
tests/unit/Architecture/         mechanical dependency and slice-shape rules
tests/acceptance/Features/       deployed-system executable specifications
tests/ui/Features/               fast bUnit component states
tests/integration/Features/      every slice through HTTP and PostgreSQL
tests/integration/Infrastructure gateway and published WASM route behavior
tests/e2e/Features/              API and Playwright workflows crossing slices
```

Integration tests are the primary proof because most slices coordinate HTTP binding, validation,
SQL, PostgreSQL constraints, and response mapping. Unit tests are reserved for deterministic logic;
they do not mock nonexistent service and repository layers. Mechanical tests protect the client
dependency direction and prevent shared resource clients/services/repositories from quietly
reintroducing horizontal layers. bUnit covers fast rendering states, while Playwright drives the
gateway-hosted WASM UI through every CRUD operation against a Testcontainers PostgreSQL database.
Authentication boundary tests use a test-only scheme to prove both anonymous rejection and public
health behavior without weakening production bearer validation.

Acceptance specifications are a separate black-box layer. Each request-level feature directory
owns its LightBDD acceptance tests, domain DSL, and API and/or browser protocol drivers; `Core/`
contains only generic fixture, transport, and scenario mechanics. Fixtures run both protocols by
default and opt out explicitly only for a channel-specific contract. The acceptance project has no
production project references and owns only its external JSON representations. Scenario aliases
resolve to unique physical values, while server-issued identifiers remain inside the driver. See
`docs/atdd-approach.md` for the test-data and time-control conventions.

## Observability boundary

The AppHost uses Aspire's Blazor hosting integration to serve the WebAssembly client through the
gateway. It provides client configuration before the runtime starts and maps the browser's relative
`/_otlp` endpoint to an authenticated server-side proxy. The browser-safe
`symphony-test-1.ClientServiceDefaults` Razor class library contributes an
`onRuntimeConfigLoaded` JavaScript initializer, which fetches Aspire's generated
`_blazor/_configuration` endpoint before .NET starts. The WebAssembly client imports those
environment values into configuration, starts its OpenTelemetry providers explicitly, and uses an
`IHttpClientFactory` client addressed as `https+http://api`. Aspire service discovery resolves that
logical address to the gateway's generated API proxy. The WebAssembly project explicitly enables
metrics, EventSource diagnostics, and `System.Net.Http.EnableActivityPropagation`; Blazor otherwise
disables the HTTP activity propagation feature during linking. The proxy supplies dashboard
credentials, and browser HTTP spans share W3C trace context with gateway, API, and PostgreSQL spans
without exposing dashboard credentials to the browser.

The migration harness applies all ordered `V*.sql` files, so adding a migration does not require
editing test infrastructure.

## Adding a slice

1. Name the use case in command/query language, such as `SearchGreetings` or `ArchiveLanguage`.
2. Add one file under the owning capability.
3. Define only the contract that request needs.
4. Add a nested `RequestValidator` when needed and implement the simplest appropriate SQL.
5. Carry cancellation through every I/O call.
6. Return typed results and accurate OpenAPI metadata.
7. Register the slice in the capability feature file.
8. Add tests for success and relevant failure outcomes.
9. Update feature and API documentation.
10. Run formatting, build, all tests, and the dependency audit.

The repository skill at `.github/skills/build-vertical-slice/SKILL.md` gives agents the same
workflow.
